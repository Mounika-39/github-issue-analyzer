# IssueCount

Issue counts, a health score and trends for any public GitHub repository.
Paste `owner/repo`, get the numbers and charts, or compare two repos side by side.

## Features

- Total, open and closed issue counts (pull requests are excluded)
- Average days to close an issue
- **Health score** (0-100) from stale issues, unassigned issues and the close rate
- Opened vs closed per month, top labels, top assignees
- **Trend over time**: one snapshot per day is saved, so the chart grows with use
- **Compare** two repositories side by side
- Label filter, CSV download, print to PDF, dark mode, mobile friendly

## How it works

```
Browser (static/index.html)
        |  fetch /api/...
        v
FastAPI (app/main.py)
        |
        +-- service.py ----> SQLite cache (fresh for 15 min)
        |        |
        |        +--------> GitHubClient (httpx, paging) ----> GitHub REST API
        |
        +-- SQLite snapshots (one row per repo per day) ----> trend chart
```

| Module | Job |
|---|---|
| `app/main.py` | Routes, input validation, error mapping, serves the website |
| `app/service.py` | Cache-or-fetch logic, stale fallback, snapshots |
| `app/github_client.py` | Async GitHub client: paging, rate limit and error handling |
| `app/db.py` | SQLite cache and history tables |
| `app/health.py` | The health score |
| `issue_count/` | The original command-line version; its `stats.py` is shared with the API |

## API

| Endpoint | Returns |
|---|---|
| `GET /api/repos/{owner}/{repo}/summary?label=` | Counts, monthly numbers, top labels and assignees, health, cache info |
| `GET /api/repos/{owner}/{repo}/history?label=` | Daily snapshots for trend charts |
| `GET /api/compare?a=owner/repo&b=owner/repo&label=` | Both summaries, fetched at the same time |
| `GET /api/health` | `{"status": "ok"}` |

Errors use normal status codes with a `detail` message: `400` bad name, `404` repo not found,
`429` GitHub rate limit, `502` GitHub unreachable.

## Run it

### With Docker (recommended)

```
docker compose up --build
```

Open http://localhost:8000. Optionally put `GITHUB_TOKEN=...` in a `.env` file first
(see `.env.example`) to raise GitHub's rate limit.

### Without Docker

```
python -m venv .venv
.venv\Scripts\activate          # Windows;  macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

### Command-line version

```
python -m issue_count owner/repo --label bug
```

## Tests

```
pip install -r requirements-dev.txt
python -m pytest
```

The tests cover the health score, the cache and stale fallback, history snapshots, and every
API route including GitHub failures. GitHub is replaced by a fake, so no network is needed.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `GITHUB_TOKEN` | none | Server-side token for a higher GitHub rate limit |
| `CACHE_TTL_SECONDS` | `900` | How long a result is served from cache |
| `DATABASE_PATH` | `data/issues.db` | SQLite file location |

## Design decisions

- **Server-side caching.** GitHub allows 60 anonymous requests per hour. Caching results for
  15 minutes means repeat visits and shared links cost no GitHub requests.
- **Stale fallback.** If GitHub refuses a request (for example the rate limit) and an older
  result exists, that result is shown and marked stale instead of an error. A real 404 is
  never hidden this way.
- **Partial results.** GitHub refuses to page past about 10,000 items. The API returns what it
  got with `partial: true` and the page says so.
- **Input validation.** Owner and repo names are checked against a strict pattern before they
  are placed in a GitHub URL.
- **Token stays on the server.** The browser never sees it.
- **The health score is a heuristic.** The formula is in `app/health.py` and the docstring
  explains it. It is for quick comparison, not a verdict.

## Deploy

The repo includes a `Dockerfile`, so any container host works. On Render: create a new
**Web Service** from this repo, choose the Docker runtime, and add `GITHUB_TOKEN` as an
environment variable. On free plans the disk is wiped on restart, so the trend history
resets; use a persistent disk or move to PostgreSQL to keep it.

## Roadmap

- PostgreSQL instead of SQLite, for multi-instance deployments
- Scheduled background refresh so trends fill in without visits
- Rate limiting on the API itself
- Conditional GitHub requests with ETags
